## Debug: the reducer trap on `enriched_contexts`

**Symptom:** While writing `generate_posts`, almost wrote `return {"enriched_contexts": out}` to attach posts back onto each context.
**Wrong assumption:** A node that "writes" a state key replaces it.
**Root cause:** `enriched_contexts` carries the `_append` reducer because `enrich_context` is fanned out via `Send()`. Any node returning that key APPENDS — so writing the post-augmented list back would double the contexts (5 → 10).
**Fix:** Added a separate `posts_by_context` state key with no reducer. `generate_posts` writes there; `open_issue` reads from there.
**Takeaway:** A LangGraph reducer is a property of the *field*, not of the *node that wrote first*. Once a key has a reducer, every write through it merges — including from nodes that conceptually "own" the next stage.

## Built: graph routing in one conditional edge

The original plan had two separate `add_conditional_edges` calls on `split_into_contexts`: one for the empty/ok branch and one for the `Send()` fan-out. LangGraph fires *all* matching conditional edges on a node, so both would have run — sending contexts down `enrich_context` twice. Consolidated into a single router `_route_after_split` that returns either `END` or a `list[Send]`. Cleaner and matches LangGraph's intended pattern.

## Summary

**What I learned today:**
- LangGraph reducers apply to every write of that field, so the field is the unit of concurrency, not the node — see [[langgraph-reducers]].
- `with_structured_output(pydantic_model)` on the LangChain wrapper is the cleanest way to force structured JSON without prompt-side fences/escapes.
- `Send()` payloads form the *entire* sub-state the target node sees — no leakage from parent state, which forces you to make every dependency explicit.

**What surprised me:**
- The plan's `add_conditional_edges(... has_contexts)` plus a second `add_conditional_edges(... route_enrichment)` would have double-dispatched. A subtle bug in a plan that otherwise reads clean.

**What I'd do differently:**
- Build `split_into_contexts` against fixture `.brain` files BEFORE wiring the rest — implementation-1.md called this out and I built top-down instead. Will iterate on `SPLIT_CONTEXTS_PROMPT` once real notes accumulate.

## Debug: arXiv enricher without feedparser

**Symptom:** Plan-2's `requirements.txt` lists only `mcp[cli]`, `requests`, `python-frontmatter`, `python-slugify` — no `feedparser`, but the arXiv API returns Atom XML.
**Wrong assumption:** Need to add `feedparser` to the dep list to parse the response.
**Root cause:** Atom is just namespaced XML. Stdlib `xml.etree.ElementTree` with a `{"a": "http://www.w3.org/2005/Atom"}` namespace map handles `findall("a:entry", NS)`, `findtext("a:title", ...)`, and link `rel="alternate"` selection without any extra dep.
**Fix:** Parse with `ElementTree`; keep the dep list at 4 packages.
**Takeaway:** When a "feed parser" library shows up in a dep list, check whether the feed is just Atom/RSS XML — stdlib handles both, and the wins from cutting a dep accrue every time someone runs `pip install -r requirements.txt`.
